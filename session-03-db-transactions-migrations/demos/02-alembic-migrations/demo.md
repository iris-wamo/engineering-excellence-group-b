## Objective

Demonstrate safe Alembic migration authorship — going beyond `--autogenerate` — by:

1. **Adding history/activity tracking schema** (`task_assignment_history`, `task_status_history`, `activity_log`, `notification`) with correct nullable/non-nullable fields, FKs, and indexes.
2. **Adding DB-level constraints** that enforce data integrity beyond API validation:
   - `UNIQUE` on `user.email` and `project.slug`
   - `CHECK` constraints on `notification.status` and `activity_log.entity_type`
   - Named indexes following the `ix_<table>_<col>` convention
3. **Proving migration safety** by running `upgrade head` on both a clean DB and a DB populated with seed data, including a backfill step for the new `project.slug` column.

Fulfils the **Migration Safety SLO** in [`docs/slo-and-deliverables.md`](../../docs/slo-and-deliverables.md).

---

## Scenario

A task-management API has grown to need:
- Full audit history (who assigned what, when status changed)
- Outbox-style notifications (inserted inside the business transaction)
- A URL-safe project slug for routing (`GET /projects/my-project-42`)

The constraint: existing projects in production have **no slug column**. The migration must backfill slug values from names without breaking existing rows or requiring a maintenance window.

## Autogenerated vs. Hand-Edited — What Changed and Why

| Part | Generated? | Reason |
|------|-----------|--------|
| `ix_activity_log_actor_id` | ✅ Autogenerated | `Index` in `ActivityLog.__table_args__` — detected by diff |
| `ix_activity_log_entity` | ✅ Autogenerated | Composite `Index` in `__table_args__` |
| `ix_notification_task_id` | ✅ Autogenerated | `Index` in `Notification.__table_args__` |
| `ix_task_assignment_history_new_assignee_id` | ✅ Autogenerated | `Index` in `__table_args__` |
| `uq_project_slug` | ✅ Autogenerated | `UniqueConstraint` in `Project.__table_args__` |
| `ix_project_slug` | ✅ Autogenerated | `Index` in `Project.__table_args__` |
| `project.slug` **Phase A** (add nullable) | ✅ Autogenerated stub — adjusted | Autogenerate would emit `nullable=False` which fails on existing rows |
| `project.slug` **Phase B** (backfill via `UPDATE`) | ❌ **Hand-written** | `--autogenerate` cannot infer data transforms; SQL written manually |
| `project.slug` **Phase C** (`ALTER COLUMN SET NOT NULL`) | ❌ **Hand-written** | Must happen _after_ backfill or Postgres raises `column contains null values` |
| `ck_notification_status` CHECK | ❌ **Hand-written** | Autogenerate does not diff `CheckConstraint` on pre-existing VARCHAR columns |
| `ck_activity_log_entity_type` CHECK | ❌ **Hand-written** | Same reason — business rule, not schema shape |

**Key insight**: `--autogenerate` is a diff tool, not a migration author. It detects added/removed columns, indexes, and unique constraints reliably. It cannot generate safe backfill sequences or check constraints on pre-existing columns. Those must always be hand-written and reviewed.

## API vs. DB Validation — Which Layer Owns What, and Why

| Validation | API | DB | Rationale |
|------------|-----|----|-----------|
| Email format (RFC 5322) | ✅ | ❌ | DB cannot validate format rules — only stores strings |
| Duplicate email rejection | ✅ 409 response | ✅ `UNIQUE` on `user.email` | API gives friendly error first; DB is the safety net for any code path that bypasses the API |
| Slug format (lowercase, hyphens only) | ✅ | ❌ | Normalisation is an application concern |
| Duplicate slug | ✅ 409 response | ✅ `uq_project_slug` | Same dual-layer pattern as email |
| `notification.status` valid values | ✅ enum | ✅ `ck_notification_status` | DB check guards the outbox state machine from internal bugs that bypass the API layer |
| `activity_log.entity_type` valid values | ✅ app enum | ✅ `ck_activity_log_entity_type` | Audit trail must be incorruptible even from service-layer code that doesn't go through a public API |
| Task status transitions (e.g. `done → todo`) | ✅ | ❌ | State machine logic is too complex for a `CHECK` constraint; belongs in the service layer |
| Project membership required for task assignment | ✅ | ❌ | Referential integrity (FK) ensures a user exists; business rule (must be a member) lives in the service |
| FK referential integrity | ❌ | ✅ FKs with `ondelete` | Database enforces referential integrity unconditionally; API cannot guarantee this alone |

**Rule of thumb**: the API owns _what values are semantically valid_; the DB owns _what values are structurally valid_. When both layers can enforce the same rule cheaply (e.g. uniqueness), use both — the DB is the last line of defence.

**Backfill formula**: `lower(regexp_replace(name, '[^a-zA-Z0-9]+', '-', 'g')) || '-' || id`
- The `id` suffix guarantees uniqueness even when two projects share the same name.
- The `WHERE slug IS NULL` clause makes the backfill idempotent.

## What We Learned

- **`--autogenerate` is a starting point, not the finish line.** It reliably detects column additions, index changes, and unique constraints from model diffs. It does not generate backfill logic or check constraints on pre-existing columns — those must be hand-written and reviewed.
- **The 3-phase pattern for adding NOT NULL columns to live tables is essential.** `ADD COLUMN ... NOT NULL` fails immediately if any rows exist. The safe sequence is: (1) add nullable, (2) backfill all rows, (3) `ALTER COLUMN SET NOT NULL`. Autogenerate skips steps 2 and 3.
- **DB constraints and API validation are complementary, not redundant.** The API gives user-friendly errors early; the DB check constraint is the unconditional last line of defence — it catches internal service code, background jobs, and direct SQL access that bypass the API entirely.
- **Named constraints matter for downgrade safety.** `op.drop_constraint("uq_project_slug", ...)` only works if the constraint has a known name. Anonymous constraints (Postgres auto-names them) make downgrade scripts fragile.
- **The id-suffix backfill strategy** (`name-slug-id`) is a safe default when project names may collide. A pure name-derived slug would raise a unique violation mid-migration for duplicate names.
