# Demo: Alembic Migration Safety & DB-Level Constraints

## Loom Video

https://www.loom.com/share/aa22de56da7d42ebaa060e61545b327f

## Objective

Demonstrate safe Alembic migration authorship beyond `--autogenerate`:
1. **Schema for history/activity tracking** (`task_assignment_history`, `task_status_history`, `activity_log`, `notification`) with proper nullability, foreign keys, and named indexes.
2. **DB-level constraints**:
   - `UNIQUE` on `user.email` and `project.slug`
   - `CHECK` constraints on `notification.status` and `activity_log.entity_type`
   - Standardized named indexes (`ix_<table>_<column>`)
3. **Migration safety**: 3-phase zero-downtime backfill for `project.slug` on existing populated tables, plus clean rollback verification.

Fulfils the **Migration Safety SLO** in [`docs/slo-and-deliverables.md`](../../docs/slo-and-deliverables.md).

---

## Commands & Steps

```bash
# 1. Apply migration with 3-phase backfill on existing data
uv run alembic upgrade head

# 2. Verify rollback reversibility
uv run alembic downgrade -1

# 3. Re-apply to head and run tests
uv run alembic upgrade head
uv run pytest
```

In **DBeaver**, verify the backfilled slugs and test the 4 DB constraint rejections.

## Autogenerated vs. Hand-Edited

| Component | Status | Rationale |
|---|---|---|
| Named Indexes (`ix_*`) | ✅ Autogenerated | Detected from `__table_args__` index definitions |
| `uq_project_slug` | ✅ Autogenerated | Detected from `UniqueConstraint` on `project` |
| `project.slug` **Phase A** (Add nullable) | ✏️ Adjusted | Changed `nullable=False` stub to `True` so existing rows don't fail |
| `project.slug` **Phase B** (Backfill SQL) | ❌ **Hand-written** | `--autogenerate` cannot infer safe slug generation logic |
| `project.slug` **Phase C** (`SET NOT NULL`) | ❌ **Hand-written** | Applied after backfill completes to guarantee zero null rows |
| `ck_notification_status` | ❌ **Hand-written** | Autogenerate does not detect `CheckConstraint` on existing columns |
| `ck_activity_log_entity_type` | ❌ **Hand-written** | Business rule check constraint on audit trail |

## API vs. DB Validation Ownership

| Validation | API Layer | DB Layer | Rationale |
|---|:---:|:---:|---|
| Email format (RFC 5322) | ✅ | ❌ | Regex and semantic validation belongs in API/Pydantic schemas |
| Duplicate email rejection | ✅ 409 | ✅ `UNIQUE` | API gives friendly error; DB is the safety net for concurrent writes or direct scripts |
| Slug format & normalisation | ✅ | ❌ | Lowercase kebab-case conversion is an application concern |
| Duplicate project slug | ✅ 409 | ✅ `uq_project_slug` | Dual-layer protection guarantees routing integrity |
| `notification.status` values | ✅ Enum | ✅ `CHECK` | DB check protects outbox state machine from background job bugs |
| `activity_log.entity_type` | ✅ Enum | ✅ `CHECK` | Immutable audit trail integrity |
| State transitions (`done → todo`) | ✅ | ❌ | Complex business workflows belong in service layer |
| FK Referential Integrity | ❌ | ✅ `ON DELETE` | Relational integrity is guaranteed unconditionally by PostgreSQL |

## Actual Findings & Evidence

### 1. Upgrade & 3-Phase Backfill (Seeded DB)
```text
$ uv run alembic upgrade head
INFO  [alembic.runtime.migration] Running upgrade 096305ddb2ff -> cd823c0995ed, add_project_slug_and_db_constraints
```
All 5 existing projects received backfilled slugs (`taskflow-backend-mvp-1`, `database-migration-suite-2`, etc.) via:
```sql
UPDATE project
SET slug = lower(regexp_replace(name, '[^a-zA-Z0-9]+', '-', 'g')) || '-' || id::text
WHERE slug IS NULL;
```

### 2. Constraint Violations in PostgreSQL (DBeaver)
```sql
-- 1. Duplicate user email → user_email_key
INSERT INTO "user" (name, email) VALUES ('Clone', 'morgan.smith1@example.com');
-- ERROR: duplicate key value violates unique constraint "user_email_key"

-- 2. Duplicate project slug → uq_project_slug
INSERT INTO project (name, slug) VALUES ('Dup', 'taskflow-backend-mvp-1');
-- ERROR: duplicate key value violates unique constraint "uq_project_slug"

-- 3. Invalid notification status → ck_notification_status
INSERT INTO notification (recipient_id, type, status) VALUES (1, 'TEST', 'dispatched');
-- ERROR: new row for relation "notification" violates check constraint "ck_notification_status"

-- 4. Invalid activity log entity → ck_activity_log_entity_type
INSERT INTO activity_log (entity_type, entity_id, action) VALUES ('invoice', 99, 'CREATED');
-- ERROR: new row for relation "activity_log" violates check constraint "ck_activity_log_entity_type"
```

### 3. Clean Revertability & Test Suite
```text
$ uv run alembic downgrade -1
INFO  [alembic.runtime.migration] Running downgrade cd823c0995ed -> 096305ddb2ff, add_project_slug_and_db_constraints

$ uv run alembic upgrade head && uv run pytest
69 passed in 2.96s
```

## Key Takeaways

1. **`--autogenerate` is a scaffold, not an author:** It detects shape differences but cannot generate safe backfills or detect check constraints on existing columns.
2. **3-Phase Pattern for Live Tables:** Always add columns as nullable first, populate existing rows with idempotent SQL, and then enforce `NOT NULL` and uniqueness.
3. **Defense in Depth:** API handles user-friendly errors; DB check and unique constraints guarantee absolute data integrity.
